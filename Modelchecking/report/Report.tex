\section*{Introduction}

This report covers Promela models of two concurrent programs and the
verification of their correctness properties using Spin. The first
program is a first-come first-served (FCFS) process scheduler, one of
three policies supported by a shared-memory process manager. A team of
OpenMP threads dispatches processes from a common ready queue, moves
them to a waiting queue when a resource is unavailable, and updates a
shared resource table, with nested locks protecting these structures
and new processes arriving while the threads are already running. The
second program is a distributed Othello engine running a parallel
alpha-beta search. An MPI master hands candidate moves out to worker
processes as they report back, propagates a shared alpha bound between
them, and reduces the search depth partway through a round when the
turn clock runs down. It communicates over three channels: MPI
collectives to start a round, point-to-point messages to distribute and
collect work, and a socket to the referee.

Parts of each program were omitted, some behaviour was replaced with
nondeterministic choices, and the remaining parameters were fixed to small
values. These three moves do not affect the results in the same way, so it
helps to separate them with the usual pair of terms. An abstraction is
\emph{sound} for a property if every counterexample it reports corresponds to
a real execution of the implementation, meaning there are no false alarms. It
is \emph{complete} if every violation the implementation can commit also
appears in the model, meaning there are no missed defects.

Replacing concrete behaviour with a nondeterministic choice adds executions
rather than removing them, which is why Promela treats nondeterminism as the
standard way to build an abstraction \cite{inggs_promela}. That direction
keeps completeness but puts soundness at risk, because the model can now do
things the implementation never would. Fixing the parameters to small values
and leaving components out works the other way: it removes executions, so a
counterexample that survives is still a real one, but a property that passes
has only been shown to pass inside the bound. Neither model here is purely one
or the other, so both directions are handled explicitly. Every counterexample
is read back against the C source before it is called a defect, and every
passing result is reported with its configuration attached rather than as a
general claim. Each abstraction is justified where it is introduced, and
Section~\ref{sec:limits-1} and Section~\ref{sec:limits-2} give the specific
limits for each program.

The analysis found defects in both programs. For the scheduler, 6 of the 
7 checks failed, with the counterexamples tracing back to two faults in 
\code{manager.c}: a resource request that does not check whether the requester 
already owns the resource, and a dispatch loop that accesses shared process 
state without holding a lock. For the Othello engine, 4 of the 5 checks 
failed, with 3 faults identified in \code{my\_player.c}, namely an initialiser 
escaping from the minimax minimising branch as if it were a score, comparisons 
between scores calculated at different search depths, and two referee message 
types for which the master loop has no corresponding branch. The last fault 
did not occur in any recorded match, illustrating the value of model checking 
in finding behaviours that testing may not expose.

\section{Program 1: FCFS Process Scheduler}

% ---------------------------------------------------------------------
\subsection{The Promela Model}

The model abstracts the FCFS path of \code{manager.c}: \code{schedule\_fcfs}
together with \code{execute\_instr}, \code{request\_resource},
\code{release\_resource}, \code{enqueue\_pcb}, \code{dequeue\_pcb} and
\code{terminate}. It consists of an \code{init} process that seeds the ready
queue, three inlines standing for \code{terminate}, \code{request\_resource}
and \code{release\_resource}, and a \code{Worker} proctype instantiated once
per scheduling thread. The other two policies are not modelled: all three sit
on the same queues, locks and resource table, so including them would have
multiplied the state space without reaching a different class of defect.

Four constants fix the size of the model, each the smallest value that still
shows the behaviour of interest. \code{NUM\_WORKERS} is 2, because a single
thread cannot interleave with anything. \code{NUM\_PROCS} is 3, because with 2
processes one running and one blocked leaves the ready queue empty, and a
third is needed before a process can be dispatched while another is already
blocked. \code{NUM\_RESOURCES} is 2, the smallest number admitting a circular
wait \cite{silberschatz2018}. \code{MAX\_INSTR} is 3, enough for a process to
request a resource, release it and request again, so that a release can wake a
blocked process. Identifiers start at 1 so that 0 can stand for \code{NULL}
and \code{resource\_owner[r] == 0} reads exactly as
\code{resource->allocated == NULL} does. Only \code{MAX\_INSTR} is wrapped in
an \code{\#ifndef} guard, since it is the one parameter varied between runs;
supplying it with \code{spin -D} means every result in
Section~\ref{sec:results-1} comes from the same committed file.
Table~\ref{tab:mapping} sets out the correspondence between the
implementation and the model.

OpenMP nested locks were used to protect the shared structure in the implementation,
which let a thread reacquire a lock it already holds \cite{openmp52};
\code{schedule\_fcfs} takes \code{i\_lock} and then calls
\code{execute\_instr}, which takes it again. The model represents no locks at
all, only the \code{atomic} blocks standing for the regions they protect. That
is sound provided the locks cannot deadlock against each other, which is
checkable by inspection: every FCFS path acquires them in the same order, and
\code{release\_resource}, the only function holding two queue locks at once,
always takes \code{q\_locks[1]} before \code{q\_locks[0]}. With a consistent
acquisition order no circular wait between locks is possible
\cite{silberschatz2018}. One caveat to note is that a blocking statement inside an
\code{atomic} sequence causes Spin to drop atomicity rather than report an
error \cite{spin_atomic}, so the sends on \code{ready\_q} and
\code{waiting\_q} could in principle interleave, but both channels are sized
at \code{NUM\_PROCS} and can only fill if a PCB is enqueued twice, which is
what \code{no\_dup\_ready} exists to rule out.

What the model leaves outside an \code{atomic} block matters more. The
assignment \code{running\_p->state = RUNNING}, the loop guard
\code{while (running\_p->state == RUNNING)} and the test
\code{if (running\_p->state == WAITING)} all touch shared PCB state with no
lock held, since \code{i\_lock} is released as soon as \code{execute\_instr}
returns. Those statements sit outside any atomic block in the \code{Worker}
loop, so \code{pan} is free to interleave the second worker there. Wrapping
them in \code{atomic} for tidiness would have left the model unable to find
the defect in Section~\ref{sec:results-1}.

\begin{lstlisting}[style=clang,caption={Unprotected reads in \code{schedule\_fcfs}, abridged}]
running_p->state = RUNNING; /* no lock held */
while (running_p->state == RUNNING) /* no lock held */
{
  ...
  omp_set_nest_lock(&i_lock);
  ...
  execute_instr(running_p);
  omp_unset_nest_lock(&i_lock); /* lock released here */

  load_new_processes();

  if (running_p->state == WAITING) /* no lock held */
  {
    break;
  }
  running_p->next_instruction = running_p->next_instruction->next;
  ...
}
\end{lstlisting}

Two arrays in the model do not have direct counterparts in \code{manager.c};
\code{executing[]} keeps track of how many workers are currently processing a 
PCB, while \code{in\_ready[]} tracks how many times a PCB appears in the ready 
queue. Since neither is used in a guard, they cannot enable or block any 
transitions; only provide the state needed by \code{pcb\_mutex} and 
\code{no\_dup\_ready}.

The instruction stream is where the model makes the biggest abstraction, because
the implementation reads instructions from a linked list created by the loader, 
where each instruction has a type and resource name. The model does not 
include these instruction records; instead, \code{select} non-deterministically 
chooses a resource, while a two-branch \code{if} non-deterministically 
chooses between a request and a release \cite{inggs_promela}. 
Because \code{pan} explores both branches, the model covers every possible 
instruction sequence of up to \code{MAX\_INSTR} steps, including sequences that 
the actual loader would not produce.
Table~\ref{tab:omissions} lists what was left out and what each omission
costs.

Three changes were needed because of how Promela works. An \code{if} 
statement with no executable guard blocks, so the test after an instruction
uses two explicit guards for \code{WAITING} instead of a guard and an 
\code{else}. Spin also doesn't allow \code{else} to be used with channel 
operations, so the dequeue uses \code{nempty(ready\_q)} and 
\code{empty(ready\_q)} as two explicit cases.

A worker can try to dequeue a process before the ready queue has been filled,
because the \code{active} proctypes start at the same time as \code{init}. 
The \code{empty(ready\_q)} branch handles this case, but it also 
causes the simple liveness failures discussed in Section~\ref{sec:results-1}.

\subsubsection*{Limits on interpretation}
\label{sec:limits-1}

The model was written by hand, so a counterexample is treated as a possible 
defect until its interleaving has been checked against the source code. 
This is done for each finding in Section~\ref{sec:results-1}. On the other 
hand, a property that holds only applies to the model configuration of 3 
processes, 2 workers, 2 resources, and \code{MAX\_INSTR} steps. One important 
assumption is that the model treats unprotected reads of 
\code{running\_p->state} as ordinary reads that see the most recent value 
written. OpenMP does not guarantee this behaviour without a 
\code{flush} \cite{openmp52}. Consequently, the real program may have behaviours 
that are not represented in the model. This means that the identified defects are a 
lower bound on the problems with the unlocked dispatch loop.

\subsection{Correctness Properties}
\label{sec:props-1}

Seven checks were run: 6 properties written as named \code{ltl} blocks in
\code{model.pml}, plus a deadlock check that is not an LTL property.
Table~\ref{tab:props} gives each formula as it appears in the file, where
\code{[]} is $\always$ and \code{<>} is $\eventually$ \cite{inggs_properties}. 4 are safety
properties, which say a bad state is never reached and are violated by a
finite prefix, and 2 are liveness properties, which say something good
eventually happens and can only be violated by an infinite execution
\cite{inggs_properties}. Promela has no quantifier, so every conjunction over
the three process ids is written out by hand.

\begin{table}[htbp]
\centering
\caption{The six LTL properties as written in \code{model.pml}.}

\begin{tabular}{l l p{9.4cm}}
\toprule
\textbf{Property} & \textbf{Class} & \textbf{Formula} \\
\midrule
\code{pcb\_mutex} & safety &
\code{[] (executing[p] <= 1)} for each \code{p} \\
\addlinespace
\code{no\_self\_wait} & safety &
\code{[] (waiting\_for[p] == 0 || resource\_owner[waiting\_for[p]] != p)} \\
\addlinespace
\code{waiting\_consistent} & safety &
\code{[] (pcb\_state[p] != WAITING || waiting\_for[p] != 0)} \\
\addlinespace
\code{no\_dup\_ready} & safety &
\code{[] (in\_ready[p] <= 1)} \\
\addlinespace
\code{all\_terminate} & liveness &
\code{<> (pcb\_state[1] == TERMINATED \&\& ... \&\& pcb\_state[3] == TERMINATED)} \\
\addlinespace

\bottomrule
\end{tabular}
\end{table}

\noindent
\textbf{\code{pcb\_mutex}} is an important invariant because the PCB 
represents a unit of work, so only one thread should process it at a time. 
The dequeue operation is protected, but the code after it is not. This means 
two threads could enter the instruction loop for the same PCB, causing both 
to update \code{next\_instruction} and \code{state}.

\medskip\noindent
\textbf{\code{no\_self\_wait}} checks the behaviour of \code{request\_resource}. 
The function only checks whether \code{resource->allocated == NULL} and does 
not check whether the resource is already owned by the requesting process. 
This results in a process being able to request a resource it already holds 
and be placed on \code{waitingq}. Since the process is the one holding the 
resource, it cannot release it while waiting. Unlike the other safety 
properties, this failure does not depend on a particular thread interleaving
(so it is considered separately).

\medskip\noindent
\textbf{\code{waiting\_consistent}} checks that a PCB in state 
\code{WAITING} is actually waiting for a resource, since the state and resource
information are updated separately without a lock protecting both operations. 
This means a PCB can enter the \code{WAITING} state without having a resource 
recorded. It can then remain on the waiting queue without anything being able 
to wake it. This property is considered together with \code{pcb\_mutex}, 
because it shows how overlapping access can lead to incorrect state that 
affects later decisions.

\medskip\noindent
\textbf{\code{no\_dup\_ready}} checks the three places that add processes 
to the ready queue: the long-term scheduler, \code{load\_new\_processes}, 
and \code{release\_resource}. A duplicate entry could cause the same process 
to be dispatched twice and lead to another \code{pcb\_mutex} violation that 
cannot be prevented just by locking the dispatch loop.

\medskip\noindent

\textbf{\code{all\_terminate}} is checked separately from the program's own 
stopping condition because they don't ask the same question. 
\code{terminate()} returns TRUE when all processes have been placed in either 
the waiting or terminated queues. This means a process that is blocked 
forever can still allow the workers to exit and the scheduler to report that 
it has finished.

\medskip\noindent

\textbf{\code{ready\_dispatched}} checks whether the system actually serves 
processes before stopping. It is only checked for process 1 because the 3 
processes are symmetric. FCFS does not use a priority field, and all 3 
instruction sequences are generated using the same nondeterministic choice. 
Therefore, checking one process represents the others and keeps the never 
claim smaller. This is an assumption based on symmetry rather than a formal 
proof, and it is the one property in Program 1 that was weakened to reduce 
the verification cost. Both liveness properties are checked under weak 
fairness, as discussed in Section~\ref{sec:results-1}.

\medskip\noindent
\textbf{Deadlock} is checked with Spin's invalid end state detection, which
asks whether any process is stopped somewhere other than a valid halting
point \cite{inggs_properties}. That is broader than asking whether a circular
wait exists \cite{silberschatz2018}; it catches a process blocked on a guard
that can never become executable, whatever the reason. Since \code{pan}
disables the check while a never claim is active, this run uses a separate
claim-free verifier \cite{spin_pan}.

\medskip\noindent
Three things were deliberately not checked, namely an assertion bounding
\code{instr\_count} was removed, because the deadlock trail already shows the
same overrun and an active assertion would let other runs stop on it rather
than on their named property. \code{detect\_deadlock} is not verified, because
it runs inside \code{\#pragma omp single} and contains no concurrency. Lock
reentrancy is not modelled, because no property depends on nesting depth,
only on which accesses are protected.

\subsection{Verification Results and Analysis}
\label{sec:results-1}

Each run selects a specific claim using \code{./pan -a -N name}. If \code{-N} 
is not provided, \code{pan} uses the first claim in the file by default. 
The deadlock check uses a second binary compiled from the same generated 
\code{pan.c} with \code{-DNOCLAIM}. This removes the claims from the verifier,
rather than from the model itself \cite{spin_pan}. The value of 
\code{MAX\_INSTR} is also supplied to \code{spin} on the command line, 
ensuring that all results in Table~\ref{tab:results} use the same source file.

Two flags are used throughout the verification. \code{-m} increases the maximum 
search depth from the default of 10,000, while \code{-w26} increases the hash 
table size to $2^{26}$ entries. The larger hash table was needed because the 
default $2^{19}$ entries caused many hash conflicts at this scale 
\cite{spin_pan}. All runs were performed from the command line using 
Spin 6.5.2 on a machine with 7,GB of RAM. iSpin was not used.

Six of the seven checks failed, but they do not describe six problems. They
collapse into two defects.

\subsubsection*{The double dispatch race}

\code{pcb\_mutex} fails at depth 901 when \code{executing[]} reaches 2. After 
checking the counterexample against \code{manager.c}, the interleaving is as 
follows. Worker A dequeues process $p$ and runs an instruction requesting a 
resource held by another process. \code{request\_resource} then sets $p$ to 
\code{WAITING} and adds it to \code{waitingq}. A releases \code{i\_lock} and 
is about to check \code{running\_p->state == WAITING} to decide whether to 
leave the loop. Before this happens, worker B releases the resource, causing 
\code{release\_resource} to move $p$ back to \code{readyq} and set its state to 
\code{READY}. B then dequeues $p$ and starts running it. A reads the updated 
\code{READY} state, does not leave the loop, and continues running $p$ as well.

\code{waiting\_consistent} fails 61 steps later in the same part of the execution. 
The trail shows a PCB in the \code{WAITING} state even though the resource it 
was waiting for has already been released by the other worker. Since 
\code{release\_resource} only wakes a waiting process when the resource
matches the one it is waiting for, this PCB remains in \code{waitingq} with 
no way to return to the ready queue. It also continues holding a resource 
that it will never release.

The deadlock run is the same defect from the consequence side. Its final state
has \code{instr\_count[2]} at 4 with \code{MAX\_INSTR} at 3, leaving a worker
stuck at the selection on \code{instr\_count} because neither guard is
executable. In \code{manager.c} that is two threads both running
\code{running\_p->next\_instruction = running\_p->next\_instruction->next} for
the same PCB, so the second advances a pointer already at the end of the list
and dereferences past it. C defines no behaviour there, and a Promela control
point with no executable transition is a state with no defined successor, so
the abstraction has nothing defined exactly where the implementation has
nothing defined.

The fix is to hold a lock across the state test and the branch that follows
it, not only across \code{execute\_instr}. Doing that with \code{i\_lock}
costs parallelism, since \code{i\_lock} already serialises every instruction
in the system; a per-PCB lock is the cheaper version, because then only
threads touching the same PCB serialise.

\subsubsection*{Self deadlock in \code{request\_resource}}

This counterexample is much smaller than the others, failing at depth 379 
after 188 states. The trail only contains one worker, and \code{executing[]} 
never becomes greater than 1, so there is no thread interleaving involved. 
This is simply a logic error that a single thread can reach on its own. The 
fix is to add a check before the availability test so that 
\code{resource->allocated == cur\_pcb} is treated as a successful request. 
The same \code{!resource\_found} branch is also used when the requested 
resource does not exist. These are two different cases, so the fix should 
distinguish between a resource already owned by the process, a resource held 
by another process, and a resource that does not exist.

This defect also explains both liveness failures and has another consequence 
that is not checked by the model. \code{detect\_deadlock} searches for cycles 
in the waiting queue, and a process waiting for a resource that it already 
owns creates a cycle of length 1. The program would therefore report a 
deadlock even though it is not the type of deadlock the diagnostic is 
intended to detect. A single missing check therefore causes a safety 
violation, 2 liveness violations, and an incorrect deadlock diagnosis.

\subsubsection*{Liveness and fairness}

Both liveness properties also fail without \code{-f}, at depth 14 after 25
states, and neither of those results is evidence of anything. The cycle they
report is one in which \code{init} evaluates its loop guard and is never
scheduled again, so \code{ready\_q} is never seeded and a worker spins on an
empty queue forever. No OpenMP runtime passes over a thread that can make
progress indefinitely \cite{openmp52}, and weak fairness excludes exactly
those cycles \cite{inggs_properties}, so every liveness result reported here
uses \code{-f}. Fairness is not free: \code{ready\_dispatched} finishes in 25
states without it and explores 11\,372\,991 with it.

The fair \code{all\_terminate} counterexample ends with all three processes
\code{WAITING}, process 1 holding resource 1 while waiting for resource 1, and
both workers already exited because \code{check\_terminate} counts every
process as blocked. \code{ready\_dispatched} fails for the same reason but
exposes a separate design consequence; which is the stopping condition retires the
workers as soon as everything is blocked, so a process can still be on the
ready path when the system decides it is finished.

\subsubsection*{The property that holds}

\code{no\_dup\_ready} was checked exhaustively at \code{MAX\_INSTR 2} with 0
errors over 20\,861\,451 states in about 21 seconds, using 2\,421\,MB. The run
also reported 0 of 12 states unreached in \code{init} and 0 of 119 unreached
in \code{Worker}, which is what makes the pass worth quoting: every control
point was visited, so the result is not an artefact of dead code in the 
abstraction \cite{inggs_spin}.

The reduced bound is necessary because of the size of the state space. Failed 
properties are relatively cheap to check because the search stops when the 
first counterexample is found. However, a property that passes must explore 
all reachable states. The state space grows by about a factor of 50 for each 
additional instruction. 420,705 states at \code{MAX\_INSTR\ 1} and 
20\,861\,451 at 2, which would result in roughly $10^9$ states at 3. 
With \code{pan} reporting 96 bytes per state, this would require around 
100\,GB of memory, compared to the 7\,GB available.

The bound of 2 is reasonable because the shortest possible duplicate requires 
a PCB to be added to the queue twice before it is removed once. This requires 
one blocking request followed by a wakeup, so two instructions are enough to 
produce the smallest possible counterexample. Increasing the bound would 
therefore mainly allow longer versions of the same behaviour. This argument is 
based on the shortest witness rather than a formal proof.

It is also important to note that the model uses a channel for the ready queue. 
A channel cannot contain two references to the same PCB in the way that an 
incorrectly maintained linked list could; this result checks the 
enqueue and dequeue behaviour rather than the pointer manipulation performed 
by \code{enqueue\_pcb}.

\subsection{The Promela Model}

The model abstracts the MPI master and worker move evaluation in
\code{my\_player.c}: \code{run\_master}, \code{execute\_master},
\code{send\_init\_moves}, \code{send\_next\_move}, \code{pop\_move} and
\code{run\_worker}. The referee is modelled as an environment process,
\code{Referee}, because a Promela model must be closed and the
communication flow through \code{comms.c} is fixed by the framework rather
than by us. The board, the search recursion, \code{evaluate} and the
Othello rules are all abstracted away. What survives of
\code{minimax\_pruning} is only which of three outcomes a search produces,
which is the least the properties in Section~\ref{sec:props-2} need.

Three constants fix the size of the model, all wrapped in \code{\#ifndef}
guards so they are supplied on the command line. \code{NUM\_WORKERS} is 3,
not an arbitrary choice: \code{common/configs.py} in the Othello project
sets \code{"threads": 4} for this game, so \code{comm\_sz} is 4, one master
and three workers, and the model matches the deployed system.
\code{MAX\_MOVES} must exceed \code{NUM\_WORKERS}, or \code{send\_init\_moves}
empties the move stack before any result comes back and the dynamic
work-redistribution branch is never taken. This was not decided in advance;
it was caught by \code{pan}'s unreached statement report at
\code{NUM\_WORKERS 3, MAX\_MOVES 3}, which named the redistribution send as
dead code, the same kind of finding \code{pan} gave for the scheduler's
duplicate-ready check. \code{MAX\_MOVES 4} is the smallest value that fixes
it. \code{MAX\_ROUNDS} bounds the \code{Referee} process so every run
terminates; it is 2 by default and varied per run in
Section~\ref{sec:results-2}.

correspondence between the implementation and the model.

The headline abstraction is \code{evaluate\_move}, which stands for the call
a worker makes into \code{minimax\_pruning} and, through it, the minimising
branch of \code{minimax}. That branch initialises an accumulator to
\code{INT\_MAX} and loops over the legal moves at that node:

\begin{lstlisting}[style=clang,caption={The minimising branch of \code{minimax}}]
minEval = INT_MAX;
legal_moves(moves, &number_of_moves, my_colour);
for (int i = 0; i < number_of_moves; i++)
{
  ...
  minEval = minimum(minEval, eval);
  beta = minimum(beta, eval);
  if (beta <= *alpha)
  {
    break;
  }
}
return minEval;
\end{lstlisting}

Three outcomes fall out of this: the loop never runs because there are no
legal moves at that node, so the function returns its initial value
unchanged; the loop runs once and stops, because the pruning test sits at
the bottom rather than the top, so a poisoned or reduced-depth call returns
its first child's value rather than a true minimum; or the loop runs to
completion and returns a genuine evaluation. The model reproduces exactly
these three outcomes as three branches of one \code{if}, resolved
non-deterministically wherever more than one applies:

\begin{lstlisting}[style=promela,caption={\code{evaluate\_move}, the abstraction of \code{minimax\_pruning}}]
inline evaluate_move(m,in_alpha,in_depth,out_score,out_alpha)
{
	if
	:: out_score = NO_EVAL
	:: (in_alpha == NO_EVAL || in_depth == DEPTH_REDUCED) ->
		select(out_score : 1 .. SCORE_MAX)
	:: (in_alpha != NO_EVAL && in_depth == DEPTH_FULL) ->
		out_score = true_score[m]
	fi;
	if
	:: out_score > in_alpha -> out_alpha = out_score
	:: out_score <= in_alpha -> out_alpha = in_alpha
	fi
}
\end{lstlisting}

\code{NO\_EVAL} stands for \code{INT\_MAX}, defined as 9, larger than every
genuine score in the abstract domain \code{1..SCORE\_MAX}, which reproduces
the one property of \code{INT\_MAX} that matters here: it wins every
comparison the master makes. \code{true\_score[]} is verification state with
no counterpart in the implementation. It fixes a genuine evaluation for
each move at the start of a round, chosen non-deterministically, so that a
property can compare the move the master played against the move it should
have played; the implementation has no such array, since the true value of
a move exists only implicitly, as whatever a correct full search would
return.

central to Section~\ref{sec:results-2}.

One refinement was forced by Promela semantics. \code{select} cannot bind
directly to an array element, so \code{true\_score[i]} cannot appear as a
\code{select} target; the model instead selects into a scratch variable and
assigns it, the same workaround used nowhere in the scheduler but needed
here because the scheduler has no array indexed by a loop variable at the
point of a \code{select}. One correctness note also worth stating plainly:
\code{bcast\_terminate} sends only the colour broadcast with a negative
value and not the board broadcast, because a worker breaks out of its loop
before reaching the board receive, so the collective sequences on both
sides still match.

\subsubsection*{Limits on interpretation}
\label{sec:limits-2}

As with Program 1, this model was written by hand, so a counterexample is a
candidate defect until checked against the source, and a property that
holds establishes nothing outside the worker, move and round counts it was
checked at. One further limit is specific to this model. Both the
\code{MPI\_Iprobe} busy-wait in \code{execute\_master} and the
\code{while (running)} loop in \code{run\_master} are spin loops in the
implementation; the model replaces both with blocking channel receives.
That changes what Spin reports for the same underlying failure: a spinning
\code{MPI\_Iprobe} that never receives anything is an infinite execution in
the implementation, which Spin would only find as a non-progress cycle and
only with \code{-l}, whereas a blocking receive on a channel nothing will
ever write to is an invalid end state, caught by the default safety check.
Both mean the master never returns, so the abstraction turns an
implementation livelock into a model deadlock, cheaper to detect and with a
shorter counterexample, and Section~\ref{sec:results-2} reports it on that
understanding rather than as a literal match to the C control flow.

\subsection{Correctness Properties}
\label{sec:props-2}

Three variables have no counterpart in \code{my\_player.c} and exist only
so a property can be stated, the same role \code{executing[]} and
\code{in\_ready[]} play in the scheduler model. \code{round\_done} is false
while a round is in progress and true once the collection loop has
finished and \code{best\_move} is final. \code{best\_true} is the largest
\code{true\_score} among the round's moves. \code{workers\_done} counts how
many workers have left their loop and can reach \code{MPI\_Finalize}.

Five checks were run: four properties as named \code{ltl} blocks, plus a
deadlock check that is not an LTL property. Table~\ref{tab:props2} gives
each formula as written in \code{model.pml}.

\noindent
\textbf{\code{no\_eval\_chosen}} targets the leaf case of \code{minimax}'s
minimising branch directly: there is no guard on
\code{number\_of\_moves == 0}, so a node with no legal moves, an ordinary
pass rather than an error, returns \code{minEval} still holding its initial
\code{INT\_MAX}. That value reaches \code{execute\_master}'s comparison
\code{if ((process\_score > max\_score) || (max\_move == -1))}, and since
\code{INT\_MAX} exceeds every real evaluation, the move that was never
searched always wins. This is a correctness property of the value the
engine plays, not merely an internal invariant.

\medskip\noindent
\textbf{\code{best\_is\_maximal}} asks whether the move \code{execute\_master}
selects is really one of the best available; \code{num\_moves > 0} excludes
the pass case, where \code{best\_move} is 0 and \code{true\_score[0]} would
be meaningless. Two independent things can break it. The first is the
\code{NO\_EVAL} leak above. The second is that the master compares scores
computed under different conditions: the search depth drops from 11 to 4
partway through a round once the turn clock passes \code{cut\_off}, and the
shared \code{alpha} means a worker that receives a high alpha prunes
earlier than one that receives \code{INT\_MIN}. Because the pruning test
\code{if (beta <= *alpha) break;} sits at the \emph{bottom} of the loop
rather than the top, a poisoned or depth-reduced call still evaluates its
first child in full and returns that child's ordinary-looking, in-range
value instead of \code{INT\_MAX}, which is why this second cause is silent
in a way the first is not. The fault injection results isolating the two
are in Section~\ref{sec:results-2}.

\medskip\noindent
\textbf{\code{no\_lost\_results}} is the property the whole work-sharing
protocol rests on, and the one expected to hold. \code{to\_master} stands
for the \code{MPI\_Iprobe} plus \code{MPI\_Recv(MPI\_ANY\_SOURCE)} pair, and
a single shared channel is the right abstraction because
\code{MPI\_ANY\_SOURCE} does not distinguish senders \cite{mpi41}. The
\code{Iprobe} loop has no escape: the time cutoff lowers \code{depth} but
never breaks it, so if the send and receive counts were ever unbalanced the
master would spin forever. This property confirms the balance is exact.

\medskip\noindent
\textbf{\code{workers\_finish}} asks whether every worker eventually leaves
its loop and can reach \code{MPI\_Finalize}. A worker exits only on a
negative broadcast colour, and only the \code{GAME\_TERMINATION} and
\code{UNKNOWN} branches of \code{run\_master} issue that broadcast.
\code{receive\_message} in \code{comms.c} can also return
\code{RECV\_FAILED} or \code{CLIENT\_DISCONNECTED}, and \code{run\_master}'s
if-chain has no branch for either; since \code{comms.h} is an interface the
project specification fixed and forbade changing, handling all of its
values is squarely the player's responsibility. Unlike the scheduler's
liveness failures, this one fails both with and without \code{-f}: the
cause is a missing branch, not a scheduling artefact, so the counterexample
is genuine at either setting.

\medskip\noindent
\textbf{Deadlock} is checked the same way as in Program 1, with a
claim-free verifier compiled with \code{-DNOCLAIM}, since \code{pan}
disables the invalid end state check while a never claim is active
\cite{spin_pan}. It asks whether any reachable state has a process blocked
with no executable statement while the system has stopped making progress.
This is worth stating alongside \code{workers\_finish} rather than instead
of it, because the two catch the same underlying defect through different
formulations: one says the workers never finish, the other says the system
halted somewhere it should not have.

\medskip\noindent
Two things were considered and not verified. A property comparing the
round number a worker receives against \code{round\_no} was drafted to
check that the two broadcasts, \code{bcast\_colour} and \code{bcast\_board},
stay matched; they are deliberately kept as two channels rather than
merged into one so that such a mismatch would be observable, and this
remains a natural extension rather than a checked result. Alpha
monotonicity within a round, that \code{master\_alpha} never decreases, was
also considered and dropped: it is true by construction in both the model
and the implementation, since \code{alpha} is only ever raised by a
comparison, so a property asserting it would hold trivially and establish
nothing.

\code{no\_eval\_chosen} fails at depth 205 with a single worker hitting a

is not confined to the first round either; at \code{MAX\_ROUNDS 2} the same
property fails again at depth 341 after 5\,683 states, past the point
where the first round has already closed. The match logs in
\code{othello/evidence/} confirm this happens in practice, not only in the
model: 22 of the 60 rounds in match \code{20250513\_115728} finalised on a
score of 2147483647, and workers received an \code{alpha} of that value 76
times over the same match.

\subsubsection*{The missing message-type branch}

\code{workers\_finish} fails at depth 31, and the deadlock check finds an
invalid end state at depth 20 in the same configuration; both trace to the
same missing branch in \code{run\_master} for \code{RECV\_FAILED} and
\code{CLIENT\_DISCONNECTED}. The smallest witness needs no move round at
all: at \code{MAX\_ROUNDS 0} the deadlock still appears at depth 20 after
205 states and \code{workers\_finish} still fails at depth 31 after 203
states, identical to the \code{MAX\_ROUNDS 1} numbers, which shows the
defect sits entirely in the referee message loop and has nothing to do
with move evaluation. Unlike Program 1's liveness properties,
\code{workers\_finish} fails both with and without \code{-f}: the cause is
a genuinely missing branch, not a scheduling artefact that fairness would
explain away, so no fairness argument is needed here the way one was for
\code{all\_terminate} and \code{ready\_dispatched}.

\subsubsection*{The property that probably holds}

\code{no\_lost\_results} was checked exhaustively at \code{W2, M3, R1}
with 0 errors over 7\,676\,089 states in 11.4 seconds, with zero unreached
statements in all four proctypes. At the deployed configuration,
\code{W3, M4, R1}, the same exhaustive search was killed by the kernel's
out-of-memory killer: the state vector is 244 bytes, so 7\,GB holds
roughly $2.6 \times 10^7$ states, and the search passed that without
terminating. The fallback is bitstate storage, a compile-time option that
replaces exact storage with a hash-indexed bit array so that distinct
states can collide and be treated as already visited
\cite{spin_roadmap}. That run found 0 errors over 655\,692\,780 states in
around 1\,370 seconds, but its hash factor of 6.55 is well below the 100
that indicates near-exhaustive coverage, so an appreciable fraction of the
state space may have gone unexplored. The correct claim is that no
counterexample was found in an approximate search of roughly $6.6 \times
10^8$ states, not that the property holds at three workers; the
exhaustive two-worker result is the stronger evidence, and both are
reported here rather than only the more flattering one.

The reduction to two workers is defensible for this specific property. A
lost result requires the master to close a round while a message it
should have consumed is still queued, and the shortest such witness needs
only one worker whose result is accounted for and one whose result is
not, which two workers already provide; a third worker would only admit
longer instances of the same shape. That is an argument about the
shortest witness, not a proof, and it establishes absence only within the
verified bound.

One search-order detail is worth recording because it affects how large
these numbers look without changing what they mean. \code{proctype
Referee}'s four terminal message branches are listed before its
\code{budget > 0} branch. Depth-first search explores a nondeterministic
\code{do} in the order written, so with the terminal branches first, a
termination counterexample is found in a few hundred states rather than
after an entire move round has already been explored, which is where the
tens-of-millions-of-states figures in earlier drafts of this model came
from. This changes only the order the search visits the state space, not
the space itself: \code{no\_lost\_results} at \code{W2, M3, R1} reports
exactly 7\,676\,089 states before and after the reordering, since that
property's search must be exhaustive either way and visits every state
regardless of order.

\subsubsection*{Proposed fixes}

Each of the three defects needs a different kind of fix.

The \code{NO\_EVAL} leak is the easiest to close. The minimising branch of
\code{minimax} needs a guard on \code{number\_of\_moves == 0} before the loop,
because a node with no legal moves is an ordinary pass in Othello and not an
error. What it should return there is a real evaluation of the current
position, which the engine already has in \code{evaluate}, rather than the
\code{INT\_MAX} the accumulator was initialised to. The maximising branch has
the same shape with \code{INT\_MIN}, so both need the guard even though only
the minimising one showed up here. A cheap second layer is to reject a score
equal to \code{INT\_MAX} in \code{execute\_master} before it is compared
against \code{max\_score}, so that a leak from anywhere else in the search
cannot reach the shared \code{alpha}.

The comparability defect is a design change rather than a missing test. The
master lowers \code{depth} from 11 to 4 in the middle of a round, then
compares results computed on either side of that change as though they were on
the same scale. The smallest correct version is to apply the new depth only
from the next round, so that every score within a round comes from a search of
the same depth. If the turn clock genuinely cannot wait, the alternative is to
tag each result with the depth it was computed at and keep the best move from
the deepest completed depth, discarding the shallower results instead of
mixing them in. Table~\ref{tab:fault} is what makes this worth the effort:
fixing the leak alone leaves \code{best\_is\_maximal} violated.

The missing message branch is the smallest fix of the three, and the safer
form of it is not to add two more \code{else if} arms for
\code{RECV\_FAILED} and \code{CLIENT\_DISCONNECTED}, but to give the
if-chain a final \code{else} that sets \code{running = 0} and issues the
termination broadcast. Naming the two values explicitly fixes today's defect;
a default arm also covers any value \code{comms.h} might gain later, which
matters because the interface is fixed by the framework and the player cannot
change it. Either way the workers stop blocking in \code{MPI\_Bcast} and
reach \code{MPI\_Finalize}, which is what \code{workers\_finish} asks for.

\subsection*{Program 2: Othello}

Model version: commit \code{70b73d2}.

Every result in Table~\ref{tab:results2} and Table~\ref{tab:fault}, except
the three-worker \code{no\_lost\_results} run below, is produced by a single
script:

\begin{lstlisting}[language=bash,caption={Build and run everything}]
cd Modelchecking/othello
./verify.sh
\end{lstlisting}

This regenerates \code{pan.c} and rebuilds both binaries before each group
of runs, writes every error trail to \code{results/}, the full \code{pan}
output of every run to \code{results/logs/}, and a summary table to
\code{results/summary.txt}. Passing \code{quick} as the first argument
skips the two exhaustive runs (configurations D and E) for a faster,
partial regeneration.

The three-worker exhaustive \code{no\_lost\_results} run is excluded from
the script because it exceeds available memory; its bitstate fallback
takes roughly 23 minutes and is a deliberate one-off rather than a routine
result, so it is run manually:

\begin{lstlisting}[language=bash,caption={Three-worker \code{no\_lost\_results}, bitstate fallback}]
spin -DNUM_WORKERS=3 -DMAX_MOVES=4 -DMAX_ROUNDS=1 -a model.pml
gcc -O2 -DBITSTATE -o pan_bit pan.c
./pan_bit -a -N no_lost_results -m100000 -w32
\end{lstlisting}
